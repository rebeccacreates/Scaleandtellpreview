# V3.18 staging setup: not a public deployment

**Never put private secrets in GitHub Pages, `index.html`, a public repository, SQL migration or browser console.** Your existing public repository stays untouched. Take and verify an independent JSON export before any change to live animal records.

1. In the designated staging Supabase project, back up existing schema and verify the V3.17 journal works. `20261016_01_keeper_state.sql` is included only as the **new-project baseline**; do not rerun it on a project where it is already installed. Review/run `20261017_02_care_push.sql` once using SQL Editor; this only creates tables and RPCs, not a scheduler. The optional `20261017_03_supporter_entitlements.sql` creates a read-only owner entitlement schema without checkout; see `SUPPORTER_CHECKOUT.md`.
2. Set `SCALE_PUSH_VAPID_PUBLIC` and `SCALE_PUSH_VAPID_PRIVATE` as the matching generated VAPID keypair. Set `SCALE_PUSH_SUBJECT=mailto:scaleandtellsupport@gmail.com`. Set `SCALE_PUSH_CRON_SECRET` to a randomly generated 32-byte-or-longer secret. Use the Dashboard **Edge Functions > Secrets**, not app source. Standard `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEYS`, and `SUPABASE_SECRET_KEYS` are injected by the platform, or the legacy equivalents if applicable.
3. Deploy the `care-push` Edge Function to staging using the `supabase/config.toml` setting `verify_jwt=false`. The function **independently validates user JWTs** for `config`/`test` and a separate strong cron secret for `dispatch`. An unconfigured function reports `ready:false`, so the app keeps the enable button hidden.
4. Test a user-owned subscription, `Send Test Notification`, rapid repeated test (rate limited), another keeper's endpoint rejection, full opt-out, and completed-task suppression. Install app on an actual iPhone Home Screen/Android device before testing delivery with browser closed. Android/iOS behavior varies with system/browser permissions.
5. In Database > Vault, create secrets `scale_push_project_url`, `scale_push_publishable_key`, and `scale_push_cron_secret` (same value as function's `SCALE_PUSH_CRON_SECRET`). Enable pg_cron and pg_net; **only after tests pass** execute `supabase/ACTIVATE_CRON_AFTER_TESTS.sql`. It triggers every 5 minutes, but the DB sends only at the keeper's chosen local hour (5 PM by default) when an unfinished reminder is due. A generic daily summary avoids lock-screen animal details. Inspect Cron job history and Edge Function logs for failures.
6. Deploy `index.html`, `sw.js`, manifest, icons and static pages together to **separate** Scaleandtellpreview staging site. Never upload just `index.html`, and do not modify the original public repo. Supabase Auth staging redirects must allow the preview origin/path. Re-test a second device, data merge, restore and signout.

## Security and reliability notes
- `care_push_register` stores only the authenticated owner; recognized HTTPS push-provider destinations only, to reduce SSRF risk. Providers can change; review and extend the allowlist only for a verified legitimate provider.
- The service-role/secret key is Edge-only and no browser code can invoke dispatcher with its own token. The scheduler bearer comes from Vault. No payment entitlement can be fabricated using theme settings.
- Per subscription/local date, delivery is claimed once and retried up to three times only if uncompleted care still exists. A crash after a successful send but before a DB acknowledgement may cause another attempt; the service worker uses one replacement notification tag. An unavailable network or OS notification settings can delay/suppress alerts; the **Care Schedule remains the source of truth**.
- A keeper's local `notificationPrefs` updates the push category registration on the same device, but if that re-registration fails, the app displays a warning; retain the app-side test before promising notifications. No media/photo content is included in push bodies.
- The privacy/deletion HTML is still an explicit **draft**. A full provider/retention/minors/billing notice, verified account deletion workflow, real billing checkout and server-verified paid entitlement remain public-release blockers.

## No live credentials in this package
This build contains the app's public Supabase publishable browser key, already present in V3.17. That key is not a secret, but RLS must be validated on the actual project. It contains **no** private Supabase, cron, payment or VAPID secrets.
